Email Verification Flow – Backend + UI Design
=============================================

High-Level Rules
----------------
- Users are created with:
    is_active = True
    email_verified = False

- Users CAN log in even if not verified.
- Most API endpoints are blocked until email_verified=True.
- Unverified users are allowed to access only:

    /auth/jwt/create/
    /auth/jwt/refresh/
    /auth/users/me/
    /auth/users/send_verification_email/
    /auth/users/verify_email_confirm/
    /auth/users/activation/
    /auth/users/reset_password/
    /auth/users/reset_password_confirm/


- Djoser activation is ALWAYS used for initial user email verification.
- Custom signed verification is used ONLY for:
    - resending verification
    - verifying changed email addresses



------------------------------------------------------------
1) NEW USER REGISTRATION FLOW
------------------------------------------------------------

Backend
-------
POST /auth/users/

Creates user:
    email_verified = False
    is_active = True

Djoser automatically sends an activation email because:

    DJOSER["SEND_ACTIVATION_EMAIL"] = True

The activation email contains:
    uid
    token

The frontend must POST those values to:

    POST /auth/users/activation/


Activation Processing
---------------------
When POST /auth/users/activation/ returns 204:

    backend signal sets:
        email_verified = True

This is handled by:

    user_activated → mark_email_verified()


Important Enforcement Model
---------------------------
Account activation does NOT control login.
Email verification controls API access.

We enforce verification using:
    IsEmailVerifiedOrAllowed (global DRF permission)



UI Behavior After Registration
------------------------------
1. Show:
       "Check your email to verify your account"

2. User may log in immediately OR later.

3. After login, ensure that the user is verified

       GET /auth/users/me/

4. If:
       email_verified == false

   redirect to:

       /verify-email-required



------------------------------------------------------------
2) LOGIN FLOW (UNVERIFIED USER)
------------------------------------------------------------

Backend
-------
POST /auth/jwt/create/

JWT response includes:

{
  access: "...",
  refresh: "...",
  email: "...",
  email_verified: false,
  first_name: "...",
  last_name: "..."
}

Login is always allowed.


UI Behavior After Login
-----------------------
If email_verified == false:

    redirect → /verify-email-required



------------------------------------------------------------
3) SCREEN: VERIFY EMAIL REQUIRED
------------------------------------------------------------

Route
-----
/verify-email-required


Purpose
-------
User must verify before accessing the application.


UI Options
----------

OPTION A — Resend Verification To Current Email

POST /auth/users/send_verification_email/

Body:
{}


OPTION B — Change Email And Verify

POST /auth/users/send_verification_email/

Body:
{
  "new_email": "new@example.com"
}



------------------------------------------------------------
4) BACKEND: send_verification_email
------------------------------------------------------------

POST /auth/users/send_verification_email/
Authenticated endpoint.


Behavior
--------
Always generates a Django SIGNED token containing:

    user_id
    email

If new_email provided:
    token contains new_email

Else:
    token contains current email

Sends email containing verification link.

Return:
    HTTP 204



Verification Email Link
-----------------------
https://frontend-host/auth/verify-email?token=SIGNED_TOKEN



------------------------------------------------------------
5) SCREEN: VERIFY EMAIL (SIGNED TOKEN LANDING PAGE)
------------------------------------------------------------

Route
-----
/auth/verify-email?token=...


UI Behavior
-----------
1. Extract token from URL
2. POST to:

       /auth/users/verify_email_confirm/

Body:
{
  "token": "..."
}



------------------------------------------------------------
6) BACKEND: verify_email_confirm (SIGNED TOKEN FLOW)
------------------------------------------------------------

POST /auth/users/verify_email_confirm/
AllowAny endpoint.


Behavior
--------
1. Validate signature
2. Validate expiration
3. Extract:
       user_id
       email
4. Load user
5. If email differs:
       update user.email
       update username if required
6. Set:
       email_verified = True
7. Save user
8. Return 204


Purpose
-------
This endpoint verifies:
    - changed email addresses
    - manual resend verification requests



------------------------------------------------------------
7) SCREEN: ACCOUNT ACTIVATION LANDING PAGE (DJOSER FLOW)
------------------------------------------------------------

This page handles links from the ORIGINAL activation email.


Route Example
-------------
/activate?uid=...&token=...


UI Behavior
-----------
1. Extract uid and token from URL
2. POST to:

       /auth/users/activation/

Body:
{
  "uid": "...",
  "token": "..."
}

3. If response = 204:
       backend signal sets email_verified=True

4. Redirect to:
       application dashboard



------------------------------------------------------------
8) UI AFTER SUCCESSFUL VERIFICATION
------------------------------------------------------------

After either verification mechanism:

    Djoser activation OR signed token verification


UI should:

1. Show success message
2. Redirect to dashboard
3. Optionally refresh JWT



------------------------------------------------------------
9) CHANGING EMAIL AFTER ALREADY VERIFIED
------------------------------------------------------------

User enters new email.


UI calls:

POST /auth/users/send_verification_email/
{
  "new_email": "new@example.com"
}

Backend:
    immediately set email_verified = False
    send signed verification email

User clicks link → verify_email_confirm → email_verified=True



------------------------------------------------------------
10) FORGOT PASSWORD (DJOSER RESET FLOW)
------------------------------------------------------------

This flow is for users who cannot log in because they forgot their password.
It uses Djoser’s built-in reset password endpoints (no new backend endpoints).

Important:
---------
DJOSER setting:
    "SET_PASSWORD_RETYPE": True

This means the backend requires BOTH:
    new_password
    re_new_password

The UI must collect and submit both fields.


10A) SCREEN: FORGOT PASSWORD (REQUEST RESET EMAIL)
--------------------------------------------------

Route
-----
/forgot-password

UI Behavior
-----------
User enters their email and submits.

Backend call:

POST /auth/users/reset_password/

Body:
{
  "email": "user@example.com"
}

Backend Behavior
----------------
Djoser sends a reset email containing:
    uid
    token

Return
------
HTTP 204


10B) SCREEN: RESET PASSWORD LANDING PAGE (FROM EMAIL LINK)
----------------------------------------------------------

Route Example
-------------
/reset-password-confirm?uid=...&token=...

UI Behavior
-----------
1. Parse uid and token from URL
2. Show form:
       New Password
       Retype New Password
3. Submit to backend:

POST /auth/users/reset_password_confirm/

Body:
{
  "uid": "...",
  "token": "...",
  "new_password": "newPassword123",
  "re_new_password": "newPassword123"
}

Return
------
HTTP 204

After 204:
    show success message
    redirect to login


Notes
-----
- Both password fields are REQUIRED by backend validation.
- UI must validate passwords match before submitting.
- These endpoints must remain allowlisted (unauthenticated users must be able to reset).



------------------------------------------------------------
11) PERMISSION ENFORCEMENT
------------------------------------------------------------

Global DRF permission:

    IsEmailVerifiedOrAllowed

Request is blocked if:
    user is authenticated
    AND email_verified == False
    AND endpoint is not allowlisted


Allowlist
---------
/auth/jwt/create/
/auth/jwt/refresh/
/auth/users/me/
/auth/users/send_verification_email/
/auth/users/verify_email_confirm/
/auth/users/activation/



------------------------------------------------------------
11) REQUIRED UI SCREENS
------------------------------------------------------------

1. Login Screen
   already exists

2. Verify Email Required Screen
   /verify-email-required
   - resend verification
   - change email + verify

3. Activation Landing Page (Djoser)
   /activate
   - parse uid/token
   - call /auth/users/activation/

4. Signed Verification Landing Page
   /auth/verify-email
   - parse token
   - call /auth/users/verify_email_confirm/



------------------------------------------------------------
FINAL ARCHITECTURE CHARACTERISTICS
------------------------------------------------------------

- Djoser activation ALWAYS used for initial verification
- Signed verification used for resend / email change
- Users never inactive
- Login always allowed
- API access blocked until verified
- Verification state stored in:
      user.email_verified
- Verification is achieved by:
      Djoser activation signal OR signed verification endpoint

Supports:
    new users
    delayed activation
    resend verification
    email changes anytime
